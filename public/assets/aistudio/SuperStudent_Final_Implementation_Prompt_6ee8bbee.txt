The database is not a text file to search line-by-line. For database records, use relational queries supported by indexes. Verify the actual Turso/libSQL features available in the connected database and deployment tier before relying on a particular index type. Illustrative SQL patterns (adapt table/column names to the verified schema and ORM; never copy them blindly if the actual schema differs):

```sql
CREATE UNIQUE INDEX IF NOT EXISTS users_email_normalized_uq
  ON users(email_normalized);

  ON users(username_normalized);

SELECT id, password_hash, status, role_version
```

1. CACHE DESIGN — DEFINE A POLICY PER DATA CLASS
============================================================

Before coding, create a short cache-policy table in the repository documentation. For every cacheable resource specify: canonical source, cache layer, cache key, TTL/freshness, stale behavior, invalidation/versioning, whether a Worker is invoked on a cache hit, and whether the data is public. Do not use one universal TTL for everything.

Use these defaults as a starting policy, then validate them against the actual routes and the currently supported Cloudflare/Turso features. If a different value is necessary, explain the reason and document it. Use seconds in configuration and readable names in code.

A. Public static assets (JS, CSS, fonts, icons, fixed decorative images)
- Serve through Cloudflare Static Assets/CDN wherever supported, without a Worker route for ordinary static requests.
- Use content-hashed filenames for build assets and long-lived immutable caching where safe.
- For stable files without hashed names, use an appropriate shorter TTL or version the URL before applying a long TTL.
- Never cache deployment-specific HTML indefinitely if it must point to new asset hashes. Confirm the SPA fallback and asset paths work after deployment.
- Do not add a Worker solely to serve ordinary static files.

B. Public PDFs and public image files
- If hosted at an eligible origin under the owner’s Cloudflare zone, configure the ordinary CDN/cache rules so that successful public file responses can be served from edge cache without invoking a Worker on a cache hit. Confirm the actual DNS/proxy/origin/route configuration supports this; do not merely assume that adding Cloudflare automatically caches an off-site provider.
- Use stable, versioned URLs for immutable file contents. When a file is replaced, generate a new versioned URL or purge the exact affected URL. Do not let the browser or CDN keep the previous file indefinitely under the same URL.
- Start with a long edge/browser TTL for immutable public file URLs (for example, up to one year only when the URL is versioned and the resource truly immutable). Use a shorter policy for non-versioned resources. Respect provider expiry and actual Cache-Control behavior.
- Never publicly cache private student proof images, private teacher/admin attachments, account documents, unpublished files, or anything whose access varies by user/role.
- An off-site provider URL is not automatically cached by the owner’s Cloudflare zone. If direct off-site hosting is used, document that Cloudflare cannot guarantee caching it in the owner’s zone. Do not silently proxy every file through a Worker as a workaround.
- If a file must be private, use an authenticated/signed access design with bounded expiry and no shared public cache; do not expose the storage-provider origin or private token.

C. Public announcements
- Canonical copy remains in Turso.
- Use a public, cacheable read representation only for published announcements and only after verifying that no user-specific information is included.
- Suggested initial edge TTL: 60–180 seconds, with a stale-while-revalidate or equivalent strategy only if supported by the selected delivery path. On publish/edit/unpublish, invalidate the affected cache key or increment a version. If invalidation is not reliably supported, use a documented short TTL and versioned snapshot strategy.
- For very high read volume, consider generating a public JSON snapshot when an administrator publishes or edits an announcement and serving that snapshot as a static/CDN-cacheable resource. A static snapshot must not contain drafts, private audiences, moderation notes, hidden author details, or role-specific data. Do not generate a separate snapshot per user.
- Paginate announcement history. A first page of 50 records is acceptable if it matches the UI; use a stable cursor for older pages. Do not download the entire announcement history at every app launch.

D. Public document catalogue / metadata index
- Turso is the source of truth for metadata, publication state, subject/section, year, file URLs, correction URLs, and visibility.
- Fetch only the page and filters required by the current view. Use server-side cursor pagination and bounded page sizes (default 50; enforce a safe maximum such as 100 unless a measured requirement justifies another value).
- Suggested edge TTL: 5–15 minutes for public catalogue queries, adjusted by query volume and the desired freshness. Invalidate or version the affected catalogue representation after document publish/edit/unpublish/delete. If broad invalidation is too expensive or unsupported, use a short TTL and a cache version that changes after writes.
- Do not preload every document record or all PDF URLs into the browser at startup. Prefetch only the next page or common metadata when measured to improve UX.
- Cache keys must include normalized public filters, sort order, cursor, page size, and schema/version where relevant. Reject invalid/oversized pagination inputs before querying the database.

E. Account, session, admin, moderation, and personalized responses
- Never put authentication/session data, password/recovery material, student private profile data, upload authorization, admin actions, moderation queue entries, private announcements, or role-dependent responses into a shared public CDN cache.
- Use `Cache-Control: private, no-store` (or the strongest appropriate no-store policy) for session and sensitive account endpoints.
- A browser-side cache may hold only explicitly approved, non-secret display data. It must not be treated as proof of identity or permission. Re-check all permissions on the server for every protected operation.
- Never store session identifiers, raw refresh tokens, passwords, password hashes, recovery codes, or secret keys in localStorage or IndexedDB.

F. Cache failures and stale data
- Cache is an optimization, not the source of truth. Turso remains canonical for durable metadata and account state.
- For a public read, if the origin/database is temporarily unavailable, serve stale data only if it was previously verified as public, has a documented maximum stale period, and can be served without leaking unpublished/private changes. Label stale data only where useful.

3. BROWSER-SIDE CACHE AND OFFLINE-FRIENDLY STORAGE
============================================================

AUTHENTICATION VS. CACHE — NON-NEGOTIABLE
- Login and registration must be verified on the server. Never place passwords in browser storage, query persistence, source code, logs, or caches. Do not store passwords, hashes, raw session tokens, refresh tokens, or recovery secrets client-side. The browser's own password manager is separate; do not build a credential vault.
- Cache can reduce database reads or origin traffic only where the architecture allows it; it does not magically eliminate a Worker invocation when the URL is routed through a Worker. Login normally requires a Worker/API request to validate credentials. Reduce repeated database reads safely through indexed lookups and a carefully designed session strategy, not by caching credentials.
- Do not publicly cache login, registration, logout, recovery, session, account, role, or personalized responses. Send explicit `Cache-Control: no-store` (and equivalent edge-cache bypass policy) for sensitive auth/account endpoints.
- Do not treat a cached email/username/display name as proof of identity. Do not trust browser-side roles or cached authorization decisions. Re-check protected actions server-side.

Use clear separation between:
1. in-memory query cache for the current page/session;
2. persistent browser cache for approved public metadata and user-owned drafts;
3. browser HTTP cache governed by server response headers;
4. Cloudflare edge cache;
5. Turso canonical records.

Suggested behavior:
- Public announcements: query cache with a short stale time (about 1–3 minutes) and bounded persistent storage only if it improves reload performance. Revalidate in the background.
- Public document catalogue pages: cache the pages and filters the user has visited for a longer period (for example, up to 6–24 hours locally), but revalidate on navigation or after the cache becomes stale. Keep the cached set bounded; do not store the whole catalogue automatically.
- User-created unsent drafts: IndexedDB is appropriate for larger structured drafts and offline editing. Keep drafts associated with the current local account context without treating the local account ID as authorization. On sign-out, offer to retain or clear drafts in a safe and transparent way; never expose one user’s drafts to another local account profile on a shared device.
- Public static assets/files: use HTTP cache headers and the browser cache. Do not download every PDF or image in advance.
- User-specific or sensitive responses: do not persist them by default. If a product requirement later demands local persistence, document data classification, encryption limitations in a browser, retention, and sign-out behavior before implementing.
- Keep storage quotas in mind; handle `QuotaExceededError`, storage denial, private browsing limitations, corrupted entries, version changes, and stale schemas gracefully.
- Browser storage is disposable. The UI must recover by refetching from the backend if data is missing, cleared, or invalid.
- Do not use localStorage for large binary files, passwords, tokens, or large document catalogues.
- Use IndexedDB only for approved drafts/metadata that need persistence, not as a replacement for server authorization or the canonical database.
- Add versioned keys and a cleanup strategy for old cache schemas. Bound entry counts/size and expiry. Avoid deleting unrelated keys owned by other application features.
- Prevent XSS before relying on persistent browser data; sanitize untrusted rich text and avoid unsafe HTML insertion.
